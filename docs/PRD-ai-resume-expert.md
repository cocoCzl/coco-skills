## Problem Statement

程序员通常拥有大量真实工作、项目、代码和文档，但很难把这些素材转化为一份针对目标岗位、突出个人贡献并经得起面试追问的简历。常见简历工具只能套模板或润色句子，容易出现以下问题：

- 不先明确目标岗位，导致一份简历同时覆盖多个方向，重点不清。
- 把项目功能、团队成果或代码库中存在的能力直接归功于使用者。
- 为追求“漂亮数据”编造性能提升、效率提升或业务规模。
- 技术栈与项目经历不能相互印证，出现无证据的“精通”。
- 项目描述像产品功能清单，缺少个人角色、关键行动、方案取舍和结果。
- 为迎合 JD 或 ATS 堆砌关键词，甚至加入使用者没有掌握的技能。
- 忽略公司内部名称、客户资料、系统标识、源码和安全信息的披露风险。
- 只检查文字，不检查 PDF/DOCX 的字体、分页、阅读顺序和 ATS 可读性。
- 只给出模型首次生成的文本，没有证据追踪、自审、修改对照或面试可辩护性检查。

使用者需要的不是“写得像简历”的文本，而是一套由 AI 驱动、证据优先、岗位定向、可审计且能够交付精美 PDF 的程序员简历工作流。

## Background and Goals

### 背景

`coco-skills` 是一个可独立安装的开源 Skill 合集。新 Skill 将作为独立顶层 Skill 发布，并沿用仓库中“清晰触发、证据门槛、能力降级、结构化验证、行为评测和本地生成物”的既有模式。

首版不尝试覆盖所有职业，而是深度服务以下技术岗位：后端、前端、全栈、客户端与移动端、测试开发、DevOps/SRE、云与平台工程、数据工程、算法与机器学习、AI 与大模型应用，以及技术负责人和架构师。

### 产品目标

1. 让使用者能够通过自然描述自己的经历生成岗位定向简历。
2. 让 AI 能在授权范围内读取本地代码库和项目文档，提取项目事实与候选贡献线索。
3. 让 AI 能读取原简历，识别最致命的问题、重大问题和一般改进项，并按需生成优化稿。
4. 支持用户描述、代码/文档、原简历和 JD 的任意组合，形成统一职业事实真源。
5. 在没有具体 JD 时生成岗位基准版；有 JD 时生成 JD 定制版。
6. 使用通用简历规则、岗位写作策略和 JD 定制三层模型，提高岗位相关性。
7. 坚持真实、可确认、可追溯、可披露和面试可辩护，不以虚构换取表面竞争力。
8. 先交付经过自审的 Markdown 初稿，用户明确确认后再生成 PDF；通过自动技术验收后，由用户完成最终视觉签收。
9. 默认生成现代技术型极简风、单栏、ATS 友好且排版精美的 1～2 页中文简历。
10. 提供可选的本地职业证据库，支持未来针对多个 JD 复用已确认事实。

### 成功定义

产品成功不是保证通过 ATS、获得面试或被录用，而是稳定生成“投递就绪简历”：事实已确认、目标已对齐、无未解决的致命问题和保密风险、核心陈述可追溯且可辩护、内容控制在 1～2 页；对 PDF，还须完成源 Markdown 绑定的自动技术验收和用户明确视觉签收。

## Solution

AI Resume Expert 由当前 Agent/大模型执行，采用以下三层专业模型：

1. **通用简历规则**：真实性、STAR 证据、个人贡献、量化边界、ATS、信息架构、篇幅和视觉规范。
2. **岗位写作策略**：针对不同技术岗位判断应优先寻找、验证和呈现哪些能力证据。
3. **JD 定制**：将具体招聘要求映射为已证实、部分证实、未证实或不相关，只使用有证据的关键词。

默认端到端流程为：

1. 明确目标岗位、目标职级、职业阶段、求职市场和简历语言。
2. 识别访谈生成、代码/文档提取、原简历诊断或混合模式。
3. 对私有材料完成授权确认，并按安全范围只读分析。
4. 建立简历素材清单，记录来源、确认状态、扫描覆盖、证据冲突和保密状态。
5. 使用对话式职业访谈补齐信息缺口，并给出项目入选建议。
6. 达到最低证据门槛后，应用通用规则、岗位策略和可选 JD 定制。
7. 生成并自审 Markdown 初稿，同时交付证据追踪表和面试追问清单。
8. 用户审阅、修改并明确确认定稿。
9. 在本地生成 PDF，完成自动技术验收，展示页面预览并记录用户视觉签收；可选更新职业证据库。

## User Stories

1. 作为目标岗位尚未明确的程序员，我希望 AI 先询问我准备申请什么岗位，以便简历有清晰定位。
2. 作为不知道具体 JD 的求职者，我希望按目标岗位和职级生成岗位基准版，以便先形成可用简历。
3. 作为已有具体 JD 的求职者，我希望 AI 对照职责和要求生成 JD 定制版，以便突出真实匹配证据。
4. 作为同时考虑多个方向的求职者，我希望 AI 建议分别生成岗位定向版本，以免一份简历失去重点。
5. 作为交叉岗位求职者，我希望 AI 能识别真正的交叉定位，以便在合理时合并后端与 AI 等能力。
6. 作为应届生或实习生，我希望简历优先展示教育、实习、课程项目、竞赛和开源证据。
7. 作为有经验工程师，我希望简历优先展示公司核心项目、系统复杂度、技术难点和结果价值。
8. 作为技术方向转型者，我希望 AI 同时保留原有可迁移能力和真实的转型证明项目。
9. 作为技术负责人或架构师，我希望简历突出关键决策、方案取舍、跨团队影响和系统演进结果。
10. 作为直接描述经历的用户，我希望 AI 从我的叙述中提取 STAR 证据，而不是要求我先学会简历术语。
11. 作为描述不完整的用户，我希望 AI 一次只问当前最关键的问题，以便自然地补齐经历。
12. 作为希望快速填写的用户，我希望可以切换为批量结构化问卷，以减少对话轮次。
13. 作为已提供充分信息的用户，我希望 AI 跳过重复问题并直接推进，以免流程变得机械。
14. 作为需要回答提示的用户，我希望 AI 给出候选回答方向和推荐，以帮助我回忆真实细节。
15. 作为重视真实性的用户，我希望候选答案在我确认前不会被当成事实写入简历。
16. 作为拥有本地代码库的程序员，我希望 AI 从源码、文档、依赖、测试和架构信息中提取项目事实。
17. 作为私有代码库的拥有者，我希望 AI 在读取前确认授权和数据处理边界，以降低泄密风险。
18. 作为安全敏感的用户，我希望默认跳过密钥、凭据、证书、个人数据、依赖目录、构建产物和大型数据文件。
19. 作为代码库用户，我希望“读取代码库”不会自动执行构建、测试、脚本或容器。
20. 作为大型仓库用户，我希望 AI 披露实际查看和跳过的范围，而不是假装读完整个仓库。
21. 作为项目成员，我希望代码中存在的能力不会被自动写成我的个人贡献。
22. 作为贡献者，我希望通过确认自己的角色、行动和结果，把项目事实转化为可信个人贡献。
23. 作为没有外部证明的用户，我希望我明确确认的真实经历仍可进入简历。
24. 作为材料存在冲突的用户，我希望 AI 暂停相关陈述并询问我，而不是擅自选择某个来源。
25. 作为没有精确数据的用户，我希望 AI 使用真实定性结果，而不是编造百分比。
26. 作为能够提供原始数据的用户，我希望 AI 帮助计算可核查量化结果，并让我确认依据。
27. 作为公司项目参与者，我希望简历默认脱敏内部项目代号、客户和系统细节。
28. 作为拥有多个项目的用户，我希望 AI 给出 2～4 个项目的入选建议、排序依据和淘汰理由。
29. 作为有工作经验的用户，我希望公司核心项目归入对应公司经历，并避免与项目章节重复。
30. 作为转型者，我希望足够深入的个人或开源项目可以作为关键补充，但明确标注真实来源。
31. 作为技能较多的用户，我希望技能熟练度由经历证据支撑，而不是用百分比或进度条自评。
32. 作为原简历用户，我希望 AI 支持纯文本、Markdown、DOCX 和文本型 PDF。
33. 作为扫描版简历用户，我希望 OCR 或视觉工具可用时进行识别，并让我确认识别结果。
34. 作为只请求审查的用户，我希望 AI 进入诊断模式，而不是擅自重写整份简历。
35. 作为请求优化的用户，我希望保留原文件，并获得审查报告、修改对照和独立 Markdown 初稿。
36. 作为 PDF/DOCX 用户，我希望工具可用时同时审查内容和视觉排版；工具不可用时明确说明仅做文本诊断。
37. 作为不信任虚假分数的用户，我希望审查使用致命、重大、一般三档，而不是伪造 ATS 匹配率。
38. 作为 JD 定制用户，我希望每项要求显示已证实、部分证实、未证实或不相关。
39. 作为重视面试表现的用户，我希望核心成果和高熟练度技能在定稿前通过面试可辩护性检查。
40. 作为审阅者，我希望 Markdown 初稿已完成事实、岗位、保密、重复、篇幅和可辩护性自审。
41. 作为注重隐私的用户，我希望 Markdown 阶段可以暂不填写联系方式，但最终 PDF 前必须补齐确认。
42. 作为招聘系统投递者，我希望 PDF 为单栏、文字可选择、阅读顺序明确且没有隐藏关键词。
43. 作为重视审美的用户，我希望 PDF 使用现代技术型极简风，排版精美并可黑白打印。
44. 作为最终交付用户，我希望只有我明确确认 Markdown 后才生成 PDF。
45. 作为工具受限的用户，我希望 PDF 无法生成时获得最终 Markdown 和可打印 HTML，并看到明确降级说明。
46. 作为长期求职者，我希望可以选择把已确认职业事实保存为本地职业证据库。
47. 作为隐私敏感用户，我希望职业证据库不会自动创建、不会保存源码，也不会写入开源 Skill 包。
48. 作为多次定制用户，我希望职业事实真源与 JD 文案分离，以免一次润色污染长期事实。
49. 作为非技术岗位用户，我希望 Skill 明确说明首版能力边界，并只提供有限通用帮助。
50. 作为离线环境用户，我希望无网页访问时仍能依靠当前大模型、Skill 内置知识和本地材料完成核心流程。

## Functional Scope

### FR-1：目标定位与请求路由

- 未提供目标岗位时，必须优先询问目标岗位，不得直接生成初稿。
- 生成前应明确目标岗位、目标职级和职业阶段；首版默认求职市场为中国大陆、简历语言为中文。
- 一份简历对应一个明确目标岗位；不同岗位生成不同岗位定向版本，明确交叉岗位除外。
- 无 JD 时生成岗位基准版；有 JD 时生成 JD 定制版。
- 支持四类入口：直接描述生成、代码/文档辅助生成、原简历诊断或优化、混合模式。
- 不支持岗位进入有限降级，不得声称专家优化或投递就绪。

### FR-2：输入材料

- 用户描述：任职、项目、职责、行动、技术方案、结果、技能和教育信息。
- 项目材料：用户明确指定范围内的源码、文档、依赖清单、测试、架构和普通配置。
- 原简历：纯文本、Markdown、DOCX 和可提取文字的 PDF。
- 扫描版 PDF、图片或截图：仅在 OCR/视觉能力可用时支持，并要求用户确认提取结果。
- JD：文本或可可靠提取文字的本地文档。
- 多种输入可合并，但必须保留各自来源和冲突状态。

### FR-3：本地代码库与私有材料安全

- 私有公司代码或文档读取前，必须确认用户有权让当前 AI 环境处理这些材料。
- 明确告知“本地文件”不代表“只在本机处理”，数据处理受当前平台政策约束。
- 默认只做静态只读分析；运行项目、构建、测试、脚本和容器需要单独授权。
- 默认跳过 `.env` 类文件、密钥、凭据、证书、个人数据、依赖目录、构建产物、大型二进制和数据转储。
- Git 历史只有在用户明确授权后读取。
- 大型仓库采用目标导向分析，并提供扫描覆盖声明。
- 输出不得复制私有源码、内部接口、域名/IP、数据表、安全配置或未公开架构细节。

### FR-4：职业事实与证据治理

- 明确区分项目事实、个人贡献、用户确认事实、待确认素材、信息缺口、证据冲突和证据差距。
- 代码、文档和 Git 信息只能证明项目事实或提供候选线索，不能自动证明个人贡献。
- 个人贡献必须由用户确认；没有外部材料佐证不构成禁止条件。
- 证据冲突必须在澄清前阻断相关简历陈述。
- 量化结果必须可计算、可追溯或可合理解释，并经用户确认。
- 缺少可靠数据时使用真实定性结果，不得由代码复杂度推导业务成果。
- 每条关键经历陈述应进入证据追踪表，并记录来源、确认和保密状态。
- 职业事实真源与目标岗位简历文案严格分离。

### FR-5：对话式职业访谈

- 默认采用“资深技术招聘顾问 + 工程师同行”的自然、专业语气，但不得冒充真人。
- 结合用户已提供的项目和上下文，一次只询问当前最影响简历质量的问题。
- 不重复询问已经能从材料确认或用户已经回答的内容。
- 给出推荐回答方向时必须标明为候选，允许用户全部否定。
- 用户可以主动选择批量结构化问卷。
- 达到最低证据门槛后停止访谈，不为走流程继续追问。

### FR-6：最低证据门槛

Markdown 初稿生成前至少需要：

- 目标岗位与目标职级。
- 基本任职时间线；应届或实习用户可使用教育和实习时间线。
- 每段入选经历中已确认的个人角色。
- 每段入选经历中已确认的关键行动或技术方案。
- 每段入选经历中已确认的可核查量化结果或真实定性结果。
- 核心技能与经历证据相互印证。
- 没有未解决的事实冲突和保密风险。

联系方式可在 Markdown 初稿阶段缺失，但最终 PDF 前必须补齐并确认。未达到门槛时只能输出简历素材清单、信息缺口和结构骨架，不能称为 Markdown 初稿。

### FR-7：岗位策略与内容选择

- 通用规则负责真实性、STAR、结构、ATS、篇幅和视觉边界。
- 岗位写作策略分别覆盖：后端、前端/客户端、测试开发、DevOps/SRE、数据工程、AI/算法、技术负责人/架构师；全栈、移动端、云与平台工程按相关策略组合处理。
- 职业阶段分别覆盖：应届/实习、有经验工程师、技术方向转型、技术负责人/架构师。
- 项目排序考虑目标相关性、个人贡献、技术复杂度、结果价值、时间新旧和面试可辩护性。
- AI 必须给出明确的项目入选建议和取舍理由，由用户最终决定。
- 有经验用户以公司核心项目为主体，并放在对应公司经历下。
- 个人或开源项目通常作为补充；在技术转型缺少公司证据时，可作为明确标注的转型证明项目。
- 技能熟练度必须由实际频率、独立完成、复杂问题处理和原理深度支撑。
- 默认使用“熟练、熟悉、了解”；“精通”需要更强证据并由用户确认。

### FR-8：简历内容与信息架构

- 个人信息采用最小必要原则：姓名、手机号、邮箱、所在城市、GitHub/博客/技术主页和目标岗位。
- 默认不加入照片、性别、年龄/生日、婚姻、籍贯、身份证号、民族、身高体重和期望薪资。
- 核心结构根据岗位和职业阶段动态组织，不固定套用 Java 模板。
- 可选章节包括工作、精选项目、实习、开源、论文/专利、竞赛、证书和奖项，仅在相关且有证据时加入。
- 默认删除无证据的自我评价、无关兴趣和低价值课程。
- 工作与项目内容不得重复粘贴；公司核心项目应保持任职归属清晰。
- 每段成果使用 STAR 证据完成访谈，正式文案压缩为“行动 + 技术/方法 + 真实结果”。
- 优先使用设计、实现、重构、优化、排查、定位、搭建、接入、迁移、自动化和标准化等具体动作。
- 技术栈应分类并与经历相互印证，不堆砌所有接触过的工具。
- 默认选择 2～4 个最有价值的项目；最终简历控制在 1～2 页。

### FR-9：JD 与 ATS 定制

- 将 JD 要求分类为已证实、部分证实、未证实或不相关。
- 允许把真实经历改写为 JD 使用的等价专业术语。
- 每个进入简历的 JD 关键词都必须有职业事实支撑。
- 未满足要求只能进入简历外的证据差距，不得伪造。
- 禁止关键词堆砌、隐藏白字、无证据技能和伪 ATS 匹配率。
- 无 JD 时不得声称已经完成具体岗位匹配。

### FR-10：原简历诊断与优化

- 诊断模式只识别问题，不自动重写整份简历。
- 问题按致命、重大、一般改进排序；不提供缺乏依据的总分和 ATS 百分比。
- 每个问题说明原文位置、判断依据、影响和修改建议。
- 优化模式保留原文件，交付独立优化稿和修改对照。
- 修改对照至少包括原文、改后、修改原因和证据依据。
- PDF/DOCX 在渲染能力可用时同时检查内容和视觉排版；否则明确标记为文本诊断。
- 视觉审查覆盖字体、字号、层级、对齐、留白、分页、拥挤度、链接和阅读顺序。

### FR-11：生成、自审与面试可辩护性

- 用户可见 Markdown 初稿不得是模型第一次未经检查的输出。
- 初稿交付前检查事实追溯、个人/团队边界、岗位适配、STAR、关键词、重复、篇幅、保密和可辩护性。
- 对核心成果和高熟练度技能生成可能的面试追问。
- 用户无法解释的陈述应降级、补充事实或删除。
- 面试追问清单独立交付，不进入简历正文。
- 事实完整且用户明确确认后才可进入 PDF 生成；要标记为投递就绪，还须完成 PDF 自动技术验收和用户视觉签收。

### FR-12：输出与 PDF

按请求和阶段交付以下产物的适用子集：

- 简历素材清单与信息缺口。
- 项目入选建议。
- 原简历审查报告。
- JD 要求覆盖表。
- 修改对照。
- Markdown 初稿。
- 证据追踪表。
- 面试追问清单。
- 经确认、自动技术验收并得到用户视觉签收的 PDF。
- 可选职业证据库更新。

PDF 要求：

- 仅在用户明确确认 Markdown 后生成。
- 使用本地转换能力，不上传到第三方在线转换服务。
- 默认采用现代技术型极简风、单栏、克制深蓝/深灰强调色。
- 文字可选择，阅读顺序稳定，黑白打印可读。
- 不使用技能进度条、复杂图表、花哨背景或影响 ATS 的双栏布局。
- 验收中文字体、分页、截断、链接、孤行、整体可读性和 1～2 页限制。
- 自动技术验收通过且提供源 Markdown 时，先处于 `visual_signoff_pending`；其 `automatic_qualified=true`，但仍不可交付。
- 只有用户查看彩色/灰度预览后明确确认，且签收记录与 PDF、Markdown、预览资源的哈希一致时，才可标记 `qualified=true`、`delivery_blocked=false`。
- CI 的真实渲染与自动检查不替代用户对特定简历的视觉签收。
- 无法生成 PDF 时，交付最终 Markdown 与可打印 HTML，并明确说明 PDF 未生成。

### FR-13：职业证据库

- 默认不持久化，只有用户明确选择后才创建或更新。
- 保存已确认的任职、项目、技能、STAR 证据、来源和保密状态。
- 不保存源码摘录、密钥、无关公司资料或针对某个 JD 的包装文案。
- 存放于用户指定的本地位置，不写入开源 Skill 包。
- 用户不授权保存时，所有职业事实仅在当前会话使用。

## Non-Functional Requirements

### NFR-1：真实性与完整性

- 不得编造项目、职位、年限、职责、技能、数字、客户、业务影响或技术决策。
- 不得把团队成果、项目功能或仓库能力默认归属于用户。
- 所有关键简历陈述必须可追溯到来源与确认状态。
- 所有未解决证据冲突必须阻断相关内容进入初稿。

### NFR-2：隐私与安全

- 采用最小读取、最小保存和最小披露原则。
- 私有材料必须有处理授权；敏感文件和敏感输出默认排除。
- 不因读取仓库而执行代码、访问网络或修改项目状态。
- 不覆盖原简历，不自动保存职业证据库，不向第三方转换服务上传私人材料。
- 所有测试示例和 fixture 必须使用虚构或充分脱敏的数据。

### NFR-3：离线优先与模型边界

- Skill 始终由当前 Agent/大模型执行；不要求在完全没有大模型时独立工作。
- 核心规则、岗位策略、审查标准、访谈框架和模板应随 Skill 提供，不依赖网页搜索。
- 无网络时仍能处理本地描述、JD、简历、代码和文档。
- 有网络时可按用户要求调研公开市场信息，但必须标注来源，且不得上传私有材料。
- 不绑定特定模型提供商，不要求 Skill 自行调用额外模型 API 或内置 API Key。

### NFR-4：可用性与对话质量

- 默认一次只问一个高价值问题，语言自然、具体、贴合上下文。
- 不重复已经回答或可从材料确认的问题。
- 候选回答方向必须允许用户否定，不得诱导夸大。
- 能力不足或工具不可用时说明边界和下一步，不伪装完成。

### NFR-5：ATS 与视觉质量

- Markdown 本身应可读、结构稳定，PDF 应为文本型而非图片型。
- PDF 单栏、阅读顺序明确、字体可靠、链接有效并可黑白打印。
- 默认 1～2 页，不通过缩小到难以阅读的字号强行压页。
- 视觉质量通过渲染检查确认，不以“文件已创建”代替验收。
- 自动技术验收与用户视觉签收是两个独立门槛；前者通过后仍不可把 PDF 称为已交付。

### NFR-6：可扩展性与可维护性

- 通用规则、岗位策略、输出模板和降级规则应保持清晰边界。
- 新职业、新市场或新语言应能通过增加独立策略扩展，而无需破坏职业事实模型。
- 复杂参考资料按需加载，避免主入口膨胀和无关上下文占用。
- 确定性解析、校验和渲染能力应可独立测试，不依赖模型措辞。

### NFR-7：可移植性与开源合规

- Skill 以通用 Agent Skill 方式工作，不依赖个人绝对路径或本地安装副本。
- 不提交真实简历、个人信息、公司源码、密钥、运行时生成物或私有配置。
- 使用的模板、字体和依赖必须允许随 MIT 开源项目合法分发或明确要求用户本地提供。

### NFR-8：大型材料鲁棒性

- 大型仓库或长文档应采用目标导向的渐进分析，不要求一次加载全部内容。
- 必须披露扫描覆盖，不因上下文限制产生全库已读的错误声明。
- 解析失败、OCR 不可靠或文件受损时停止依赖该内容，并请求可靠替代输入。

## Implementation Decisions

- 产品作为独立顶层 Skill，正式名称为 `ai-resume-expert`，中文首版定位为“AI 程序员简历专家”。
- 主入口负责触发、请求分类、能力门槛和参考资料路由；复杂知识不全部塞入主入口。
- 逻辑模块分为：通用规则、岗位策略、访谈与证据治理、原简历审查、JD 定制、输出模板、确定性校验和 PDF 渲染。
- 证据模型以职业事实真源为核心，至少表达来源、状态、用户归属确认、可披露状态、量化依据和冲突状态。
- 岗位文案是职业事实真源的派生物，不能反向修改事实。
- 请求状态至少区分：定位、材料授权与读取、证据整理、信息补齐、可生成、初稿审查、用户确认、PDF 自动验收、`visual_signoff_pending`、`qualified`、PDF 交付和有限降级。
- 代码库默认采用静态只读分析；执行代码和读取 Git 历史均不属于隐式授权。
- 原简历解析采用能力探测：能渲染时执行完整诊断，只能提取文字时执行文本诊断。
- PDF 采用本地、可重复的渲染链路；自动报告绑定源 Markdown，用户签收记录绑定 PDF、Markdown 与预览资源的哈希。PDF/Markdown 的哈希或大小、或预览的页序号/哈希/大小变化后签收必须失效；相同页面内容在新的复验目录中仅路径变化时可复验。
- 默认视觉只有一个稳定的现代技术型极简模板；更多视觉模板不阻塞首版。
- 简历生成物默认位于用户工作目录的 `reports/ai-resume-expert/`，允许用户指定其他 Skill 包外位置；职业证据库仍只写入用户明确选择的位置。
- 不使用虚构总分或 ATS 匹配率；评估以严重度、JD 要求覆盖和投递就绪门槛表达。
- 首版核心知识离线可用，当前 Agent/大模型是必需执行主体，外部网页和额外模型 API 不是依赖。
- 开源交付至少包含 Skill 主入口和面向人类的 README；参考资料、schema、脚本、示例与评测按实际需要拆分。
- 仓库总览文档同步登记新 Skill；测试、示例和评测遵循现有仓库级组织约定。

## Testing Decisions

### 测试原则

- 优先测试用户可观察的外部行为，不测试提示词细节或模型内部推理过程。
- AI 文案允许合理措辞变化；测试必要行为、禁止行为、证据状态和产物属性，不做整篇全文快照匹配。
- 使用虚构或脱敏 fixture，所有测试在临时目录生成文件，不读取或覆盖真实简历。
- 最高层行为评测与确定性契约测试互补：前者验证 Agent 决策，后者验证结构、校验和渲染。

### 最高层测试缝

1. **Agent 会话行为**：从自然语言请求开始，观察模式选择、追问顺序、门槛阻断、降级和最终交付物。
2. **完整交付物**：从已确认职业事实、目标岗位和可选 JD 开始，检查 Markdown、证据追踪、修改对照、面试追问与 PDF 的外部属性。
3. **授权材料分析**：使用脱敏仓库、项目文档和原简历，验证安全读取、扫描覆盖、证据分离、冲突阻断和保密脱敏。
4. **PDF 与视觉验收**：在真实渲染栈中检查 PDF 文本可提取性、中文字体、页数、截断、链接和版面；覆盖待签收、有效签收、缺失/伪造/陈旧签收及哈希不匹配。真实 CI 只验证自动检查，默认视觉风格仍由用户签收。
5. **发布结构**：延续仓库现有结构检查，验证独立 Skill 的必需文件和仓库级测试资料位置。

### 代表性行为矩阵

- 输入模式：直接描述、代码/文档、原简历诊断、原简历优化、混合输入。
- 岗位：后端、前端/客户端、测试开发、DevOps/SRE、数据工程、AI/算法、技术负责人/架构师。
- 职业阶段：应届/实习、有经验工程师、技术转型者、技术负责人/架构师。
- 关键边界：无目标岗位、无 JD、多个目标岗位、不支持岗位、材料不足、事实冲突、无量化数据、私有资料、敏感文件、大型仓库、OCR 失败、无 PDF 能力。
- 不必测试岗位与职业阶段的完整笛卡尔积，但每个岗位策略至少一个正向场景，每个职业阶段至少一个结构差异场景，并覆盖关键交叉场景。

### 仓库先例

- 现有 Skill 使用“用户提示 + 可观察预期行为”的 JSON 评测描述最高层 Agent 行为。
- 现有测试使用固定 fixture、临时目录和黑盒调用验证外部结果、失败降级、输入冲突和生成物契约。
- 现有仓库结构检查会发现顶层 Skill，并验证主入口与 README 是否存在。

## Acceptance Criteria

### 目标与模式

- **AC-01**：用户未提供目标岗位时，AI 先自然询问目标岗位，且不生成简历初稿。
- **AC-02**：用户提供目标岗位但没有 JD 时，生成岗位基准版，且不声称完成 JD 匹配。
- **AC-03**：用户提供 JD 时，生成 JD 要求覆盖，并仅使用证据化关键词。
- **AC-04**：用户同时提供多个明显不同的目标岗位时，AI 推荐分别生成岗位定向版本。
- **AC-05**：目标岗位不受支持时，AI 进入有限降级，不标记专家优化或投递就绪。
- **AC-06**：直接描述、代码/文档、原简历和混合请求均能被正确分类并进入对应流程。

### 证据与访谈

- **AC-07**：代码或文档中出现的能力只进入项目事实，不自动成为个人贡献。
- **AC-08**：未经用户确认的个人贡献不会进入 Markdown 初稿。
- **AC-09**：用户明确确认的真实经历在无外部证明时仍可进入职业事实真源。
- **AC-10**：相互冲突的事实在澄清前被阻断，AI 不自动选择来源。
- **AC-11**：缺少可靠数字时不生成百分比或倍数，改用真实定性结果。
- **AC-12**：量化结果能关联输入依据，并由用户确认后才进入简历。
- **AC-13**：默认访谈一次只问一个高价值问题，不重复已有答案。
- **AC-14**：候选回答方向被明确标为候选，用户可以全部否定。
- **AC-15**：用户选择批量模式时，可一次获得结构化问题清单。
- **AC-16**：未达到最低证据门槛时，只输出素材清单、缺口或骨架，不称为 Markdown 初稿。

### 代码库与隐私

- **AC-17**：私有材料读取前出现授权与平台数据政策提示。
- **AC-18**：默认扫描跳过敏感文件、依赖目录、构建产物和大型数据文件。
- **AC-19**：仅授权读取仓库时，不执行构建、测试、脚本或容器。
- **AC-20**：没有 Git 历史明确授权时，不读取 Git 历史。
- **AC-21**：大型仓库输出扫描覆盖声明，不声称完成全库阅读。
- **AC-22**：简历和审查材料不复制私有源码或未公开内部标识。
- **AC-23**：原简历始终保留，不被诊断或优化流程覆盖。

### 内容与岗位质量

- **AC-24**：项目入选建议包含推荐排序、理由和淘汰原因，并保留用户最终选择权。
- **AC-25**：有经验用户的公司核心项目归入对应公司经历，工作与项目描述无重复粘贴。
- **AC-26**：技术转型用户可使用明确标注的个人或开源转型证明项目，但不会伪装成公司经历。
- **AC-27**：核心技能能在经历中找到支撑；无证据“精通”、技能百分比和进度条不会出现。
- **AC-28**：工作和项目成果的素材使用 STAR 校验，正式文案不机械显示 S/T/A/R 标签。
- **AC-29**：JD 未满足要求只出现在证据差距中，不被写入简历。
- **AC-30**：最终内容根据岗位和职业阶段动态组织，默认选择 2～4 个高价值项目。
- **AC-31**：默认个人信息符合最小必要原则，不主动加入照片或无关敏感身份信息。

### 诊断、优化与追溯

- **AC-32**：诊断模式输出致命、重大和一般改进项，不自动生成完整重写稿。
- **AC-33**：审查结果不出现无依据的简历总分、ATS 匹配率或录用概率。
- **AC-34**：优化模式输出独立 Markdown 初稿及原文、改后、原因、证据组成的修改对照。
- **AC-35**：关键经历陈述能在证据追踪表中找到来源、确认和保密状态。
- **AC-36**：有渲染能力时，PDF/DOCX 原简历完成内容与视觉诊断；无渲染能力时明确标记文本诊断。
- **AC-37**：用户可见 Markdown 初稿已经完成事实、岗位、保密、重复、篇幅和可辩护性自审。
- **AC-38**：无法通过面试追问的高强度陈述被降级、补充或删除。

### Markdown、PDF 与持久化

- **AC-39**：Markdown 初稿无未解决事实冲突、无未确认个人贡献、无保密阻断项和大量占位符。
- **AC-40**：只有用户明确确认内容后才生成最终 PDF。
- **AC-41**：最终 PDF 前，联系方式已补齐并由用户确认。
- **AC-42**：PDF 的自动技术验收确认其为单栏、文字可选择、阅读顺序稳定、黑白打印可读，并默认控制在 1～2 页。
- **AC-43**：PDF 自动验收检查中文字体、分页、截断、链接、孤行和整体可读性；只有用户明确视觉签收，且签收与 PDF、源 Markdown、预览哈希一致时，才可作为可交付 PDF。
- **AC-44**：PDF 渲染不可用时，交付最终 Markdown 和可打印 HTML，并明确 PDF 未生成。
- **AC-45**：职业证据库只有用户明确选择时才写入用户指定位置。
- **AC-46**：职业证据库不保存源码摘录、密钥、无关公司资料或 JD 包装文案。
- **AC-47**：生成物、真实简历和职业证据库不会被写入开源 Skill 包或提交为示例。

## Out of Scope

首版明确不做：

- 产品经理、项目经理、UI/UX、纯技术支持、硬件电子、纯管理及其他非受支持职业的专家级简历。
- 美国、英国、欧盟等国际市场的专家级规则；英文只可作为有限语言转换，不声称完成海外市场适配。
- 求职信、LinkedIn 优化、个人网站、作品集网站和个人品牌运营。
- 完整面试辅导；仅提供与简历陈述相关的面试可辩护性检查。
- 学术 CV、完整论文清单和学术申请材料。
- 职位搜索、招聘网站抓取、自动注册、自动投递、消息发送和申请状态管理。
- 录用概率、ATS 通过保证、面试保证或“完美简历”承诺。
- 为匹配 JD 虚构技能、项目、职责、数据、客户、业务影响或个人主导权。
- 未经授权读取 Git 历史、执行项目代码、构建、测试、脚本或容器。
- 上传私人简历或公司资料到第三方在线转换服务。
- 默认保存用户画像、职业证据库或任何长期个人档案。
- 原样保留原 DOCX/PDF 的复杂视觉版式；首版重新生成统一 Markdown 与 PDF。
- 多套视觉主题、海报式简历、双栏创意模板、技能图表和图片型 PDF。
- 在完全没有 Agent/大模型的环境中独立运行。
- 承诺完整阅读任意规模代码库或从代码自动推导个人贡献与业务结果。
