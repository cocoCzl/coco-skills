# 本地代码与项目文档：安全取证和保密脱敏

读取仓库的目的，是提取项目事实并帮助用户回忆个人贡献，不是自动“从代码生成个人简历”。本地路径不等于只有本机处理，数据仍受当前 Agent 平台政策约束。

## 1. 授权门槛

读取任何私有公司代码、内部文档或原简历前，先用自然语言确认：

1. 用户有权让当前 AI 环境处理指定材料。
2. 用户理解本地文件的处理方式受当前平台数据政策约束。
3. 允许读取的精确根路径或文件范围。
4. 默认只做静态、只读、最小必要分析。
5. 默认不读 Git 历史，不运行代码、构建、测试、脚本或容器。

可用确认话术：

> 在读取这个公司项目之前，请确认你有权让当前 AI 环境处理所指定的代码/文档，并接受当前平台的数据处理政策。我会默认只在你指定范围内做静态只读分析，跳过敏感与生成目录；不会读取 Git 历史，也不会执行代码、测试、构建、脚本或容器。你是否授权我读取：`<用户指定范围>`？

用户只回复“可以看项目”时，不应扩大到同级目录、其他仓库、Git 历史或执行权限。授权不明确则先询问，不读取。

## 2. 权限拆分

| 能力 | 默认 | 所需授权 | 简历证据作用 |
|---|---|---|---|
| 静态读取指定代码/文档 | 需明确材料授权 | 精确范围 | 项目事实、候选贡献线索 |
| Git 历史 | 禁止 | 单独明确授权 | 变更线索，仍不自动证明主导权 |
| 构建/测试/脚本/容器 | 禁止 | 每类单独授权且确有必要 | 只验证项目行为；不能推导个人贡献 |
| 网络访问 | 不因仓库分析自动获得 | 用户请求且符合环境政策 | 公开资料补充；不得上传私有材料 |
| 修改项目文件 | 禁止 | 本 Skill 的简历任务通常不需要 | 不属于取证工作流 |

即使用户授权执行，也必须把执行与静态读取区分开，并说明可能改变工作区或产生文件的风险。首选不执行即可完成的方案。

## 3. 默认读取与跳过范围

### 可读取的典型资料

- README、架构说明、ADR、设计文档、公开/普通接口说明。
- 依赖清单和构建元数据，用于识别技术选型，不执行它们。
- 代表性源码目录、模块边界、接口定义、普通非敏感配置。
- 单元/集成测试的结构和测试意图。
- 部署描述的非敏感部分，用于理解工程能力。

### 默认跳过

- `.env`、密钥、token、密码、私钥、证书、credential 文件和 secrets 配置。
- 用户数据、个人信息、生产日志、数据库转储、抓包、备份和大型数据集。
- `node_modules`、vendor、虚拟环境、缓存、构建产物、覆盖率和生成代码目录。
- 大型二进制、模型权重、图片/音视频、压缩包和不可可靠解析的文件。
- 隐藏的凭据目录、云账户配置、内部安全策略和生产配置。
- `.git` 和提交历史，除非用户另行明确授权。

文件名并非唯一判断依据。普通配置中一旦发现疑似凭据或个人数据，立即停止读取该内容，只记录“敏感内容已跳过”，不要在输出中复述值。

## 4. 目标导向的渐进扫描

大型仓库不承诺完整阅读，按以下顺序推进：

1. 确认目标岗位、用户声称参与的项目/模块和需要验证的经历。
2. 读取顶层目录结构和非敏感入口文档，建立模块地图。
3. 读取依赖清单、架构说明和与目标经历直接相关的模块。
4. 抽取代表性实现、测试和普通配置，避免全量加载。
5. 发现候选难点后，询问用户是否由其参与，再定向深化。
6. 达到能说明项目能力与关键缺口的程度后停止，不为“扫描完整率”消耗上下文。

不得把抽样描述为“已全面分析整个项目”。

## 5. 可以提取的项目事实

按项目而非文件清单组织：

- 项目解决的问题类别和主要用户/系统边界（先脱敏）。
- 语言、框架、数据库、中间件与基础设施的实际使用线索。
- 模块边界、数据流、关键接口类型和架构约束的安全概括。
- 并发、可靠性、性能、质量、交付、可观测性、安全等工程机制。
- 测试策略、CI/CD 描述、部署方式和维护能力。
- 可能适合访谈的难点、取舍或改造点。

项目事实必须带来源摘要和扫描覆盖。不要复制源码到简历素材清单。

## 6. 不能从仓库推导的个人事实

以下都只能作为候选回答方向，必须询问用户：

- 用户是否设计、实现、重构、排查、主导或维护了某模块。
- 谁提出方案、拥有决策权、处理线上问题或推动跨团队落地。
- 项目规模、业务收入、用户量、效率提升或稳定性数字。
- 代码作者是否等于设计者，提交数量是否等于贡献价值。
- 某技术是否达到“熟练”或“精通”。

安全表述：

> 仓库中可以看到异步任务、状态记录和重试机制，这是项目事实。它们是否由你设计或实现、你负责的边界以及实际结果，还需要你确认。

## 7. 扫描覆盖声明

每次仓库分析都交付：

```markdown
## 扫描覆盖声明

- 授权根路径：<用户指定的安全概括>
- 分析方式：静态只读 / 定向抽样
- 已查看：顶层说明、依赖清单、与 <目标经历> 相关的模块和代表性测试
- 主动跳过：敏感文件、依赖、构建产物、大型二进制/数据、Git 历史
- 无法读取：<损坏、格式或权限限制；无则写“未发现”>
- 未执行：构建、测试、脚本、容器、网络调用
- 覆盖限制：本次结论只代表上述范围，不声称完整阅读全库
```

实际文件很多时只给安全类别和数量/范围概括，避免暴露内部路径。若工具能安全生成确定性清单，可在会话审计中保留，但不要自动复制到公开简历。

## 8. 从项目事实到个人贡献

1. 将观察结果标为项目事实。
2. 选出与目标岗位最相关的候选难点。
3. 一次询问一个：用户角色 → 亲自行动/方案 → 结果 → 量化依据 → 披露边界。
4. 用户确认后形成个人贡献，并保留团队边界。
5. 用户无法确认则保留项目事实或排除，不能写入个人简历。

示例：

- 项目事实：项目含多数据源元数据采集模块。
- 待确认问题：用户是否负责数据源适配、错误恢复或只是调用现成能力？
- 用户确认贡献（虚构）：独立实现两类数据源的适配层和失败日志归一化。
- 可披露文案：设计可扩展的数据源适配接口，统一连接失败与采集异常记录，便于新增数据源及问题定位。

最后一句未披露内部数据源名称，也没有虚构效率数字。

## 9. 保密脱敏方法

### 先识别风险

- 公司/客户名称是否公开且允许与项目关联。
- 项目代号、系统名称、内部组织、业务策略是否敏感。
- 域名、IP、账号、接口、表结构、数据样例或安全配置是否可反推系统。
- 数字是否属于商业机密或安全容量信息。
- 架构组合是否足以暴露未公开防护边界。

### 四步脱敏

1. **泛化实体**：客户名 → “某大型零售企业”；项目代号 → “企业级审计平台”。
2. **抽象实现**：内部接口/表名 → “任务状态接口/审计记录模型”。
3. **保留价值**：保留问题类型、个人行动、通用技术方法和结果类别。
4. **复核可反推性**：结合时间、客户、规模和技术细节检查是否仍能识别。

若用户不能确认可披露，宁可使用更高层级概括或删除。脱敏不是把源代码换成伪代码，也不是仅删除公司名。

## 10. 失败与降级

- 授权被拒绝：不读取，转为用户直接描述或公开材料。
- 路径过大：请求用户指定项目/模块，或明确采用定向抽样。
- 文件受损/不可解析：标记无法读取，不根据缺失内容下结论。
- 检测到敏感内容：停止读取相关文件并提醒用户，不显示敏感值。
- 上下文不足：保留覆盖声明和未读范围，不能假装完成。
- 无法确认个人归属：只交付项目事实与待确认问题，不生成个人成果。
