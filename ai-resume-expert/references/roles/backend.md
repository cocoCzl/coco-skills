# 后端工程师岗位策略

适用于 Java、Go、Python、C++、Node.js 等服务端岗位。目标是证明用户能在真实约束下设计、实现和维护可靠服务，而不是展示框架数量。

## 1. 路由与主线

先确认后端主线：业务服务、基础设施/中间件、数据密集型服务、交易/支付、企业平台或 AI 应用后端。再确认目标职级和主要语言生态。语言不同不改变真实性规则，但会改变 JD 关键词和面试深度。

个人简介优先回答：工作阶段、核心语言/平台、处理过的系统类型、最能证明的工程问题、目标岗位。不要写“精通所有后端技术”。

## 2. 优先寻找的证据

| 能力域 | 高价值事实 | 可接受结果 | 需要的边界 |
|---|---|---|---|
| API 与领域设计 | 接口契约、幂等、事务边界、权限、错误模型、兼容演进 | 降低调用歧义、增强一致性或可维护性 | 用户具体负责哪些接口/领域决策 |
| 并发与异步 | 任务队列、线程/协程、消息、背压、限流、重试、超时 | 避免阻塞、隔离故障、增强可追踪性 | 流量/并发数字仅在有来源时写 |
| 数据与存储 | 模型设计、索引/SQL、事务、一致性、缓存策略、迁移 | 查询更稳定、热点压力缓解、迁移风险可控 | 不能把“使用数据库”包装成数据架构主导 |
| 可靠性 | 降级、熔断、恢复、容灾、告警、故障复盘 | 缩短定位路径、减少重复故障、提升恢复能力 | 可用性/MTTR 数字需监控和用户确认 |
| 性能 | profiling、压测、瓶颈定位、资源调优、批处理 | 有依据的延迟/吞吐变化或真实定性改善 | 区分测试环境和线上结果 |
| 安全 | 认证授权、输入校验、敏感数据保护、审计 | 降低权限风险、增强审计性 | 不披露漏洞利用和内部安全配置 |
| 工程交付 | 测试、CI/CD、容器化、配置、日志、发布回滚 | 标准化交付、降低部署复杂度 | 日常部署不等于平台架构 |
| 系统演进 | 模块拆分、迁移、兼容、技术债治理 | 控制迁移风险、提升演进效率 | 需要用户的决策与实施边界 |

## 3. 公司核心项目表达

有经验用户把最强后端项目放进对应公司经历，通常保留 2～4 个项目。每个项目一句业务/系统问题，随后 2～4 条高价值成果：

- 个人设计或实现的核心服务边界。
- 一项能深入解释的并发、数据、可靠性、性能或安全难点。
- 一项交付、迁移、故障排查或工程治理证据。
- 可核查数字或真实定性结果。

虚构脱敏示例：

> 针对批量任务占用请求线程的问题，设计异步执行、状态记录与失败重试流程，使请求可快速返回，并增强异常任务的恢复与追踪能力。

只有用户确实拥有方案边界才能用“设计”；否则改为“实现”“参与改造”或具体组件动作。

## 4. 后端禁忌

- 罗列 CRUD、增删改查、接口数量或“完成用户/菜单/权限模块”而无技术问题。
- 把 Spring Boot、Redis、Kafka 等出现过就写成精通。
- 看到微服务目录就声称“主导微服务架构”。
- 没有口径就写 QPS、P99、可用性、故障率或成本改善。
- 把团队上线、业务收入、全站稳定性直接归因于个人接口。
- 暴露内部域名/IP、表名、接口路径、账户、安全策略或源码。
- 为 JD 硬加分布式、高并发、DDD、云原生等无证据标签。

## 5. 高价值追问

一次只问当前最关键项：

1. 这个服务的请求/数据路径是什么，你个人负责的边界在哪里？
2. 最难处理的约束是并发、一致性、延迟、可靠性还是兼容性？为什么？
3. 你选择该方案时比较过什么替代方案，最终取舍是什么？
4. 一次代表性线上问题如何定位到根因？哪些观测信息起了作用？
5. 如果用了缓存/消息/异步，失效、重复、顺序、重试和失败恢复如何处理？哪些由你完成？
6. 结果来自监控、压测、发布记录还是团队观察？能披露到什么粒度？
7. 你写为“熟练”的语言/框架，处理过最复杂的问题和底层边界是什么？

候选回答只帮助回忆，不能暗示用户一定做过限流、分库分表或性能优化。

## 6. 职业阶段差异

- **应届/实习**：突出数据结构与计算机基础在项目中的真实应用、接口/数据模型、测试、调试和独立交付；课程项目不得包装成生产系统。
- **有经验工程师**：以公司核心系统为主，证明复杂问题处理、稳定交付和持续维护，个人项目从简。
- **转型者**：保留原技术域的工程证据；转后端项目需要真实 API、数据、测试和部署深度，不把简单教程当商业系统。
- **高级工程师**：增加方案取舍、跨模块一致性、容量/可靠性和系统演进证据。
- **技术负责人/架构师**：叠加 `tech-lead-architect.md`，验证决策权、迁移路径和跨团队影响；不能只列架构名词。

## 7. JD 定制提示

拆解 JD 时区分：语言基础、框架生态、数据/中间件、分布式机制、工程质量、领域经验和职级责任。

- JD 写“高并发”，只有流量约束、压测或并发控制事实才可覆盖；普通接口开发是未证实。
- JD 写“微服务治理”，只有服务治理、观测、容错或演进事实才可覆盖；使用 Spring Cloud 依赖不够。
- JD 写“数据库优化”，查询分析、索引/模型调整和结果证据可覆盖；写 SQL 本身不够。
- JD 写“架构能力”，高级方案取舍可部分/已证实；单模块实现不能扩写为整体架构。
- 领域经验可用可披露业务类别表达，不得虚构相同行业。

正文只使用已证实部分；相邻经验标“部分证实”并保持原边界。

## 8. 可辩护性检查

对核心后端成果至少能解释：调用/数据路径、自己的代码或决策边界、失败模式、替代方案、测试/观测、结果口径和方案代价。不能解释时降低动词强度、移除数字或删除技术标签。
