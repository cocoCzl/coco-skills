# AI 与大模型应用工程师岗位策略

适用于大模型应用、RAG、Agent、AI 平台、推理与 LLMOps 岗位。核心不是“接入了模型 API”，而是证明用户如何建立可靠输入、检索/工具、评估、约束、可观测和交付闭环。

## 1. 路由与主线

区分四条常见主线：

1. **LLM 应用**：Prompt、结构化输出、RAG、工具调用、Agent 工作流和业务集成。
2. **AI 平台/LLMOps**：模型网关、评估平台、可观测、路由、配额、缓存和治理。
3. **推理工程**：部署、并发、批处理、延迟、吞吐、资源与模型优化。
4. **模型研发**：训练/微调、数据与实验，主要读 `algorithm-ml.md`。

Java/后端转 AI 时可加载 `backend.md` 为次策略：公司后端经历仍是主体，真实个人/开源 AI 项目明确标注为转型证明，不伪装成公司 AI 项目。

## 2. 优先寻找的证据

| 能力域 | 高价值事实 | 可用结果 | 必须确认 |
|---|---|---|---|
| 问题与边界 | 为什么需要模型、哪些决策不能交给模型、失败代价 | 建立可用范围和人工兜底 | 不能把 demo 说成生产系统 |
| 输入/输出设计 | Prompt、schema、结构化解析、校验、重试 | 提升输出可控性、便于下游处理 | “效果更好”需评估依据 |
| RAG | 切分、索引、检索、重排、上下文、引用与权限 | 提升特定知识问题的可追溯性 | 不能把向量库接入等同完整 RAG |
| 工具调用/Agent | 工具契约、编排、状态、权限、幂等、失败恢复 | 让任务可执行、可追踪、可恢复 | 自主程度和人工确认点 |
| 评估 | 数据集、rubric、自动/人工评估、回归、错误分类 | 比较方案、阻止退化、识别失败边界 | 指标、样本和评审一致性 |
| 幻觉与安全 | 基于来源回答、验证、拒答、注入/越权防护、审核 | 降低特定风险、明确不可回答内容 | 不声称消除幻觉或绝对安全 |
| 模型与路由 | 模型选择、fallback、供应商兼容、质量/成本/延迟权衡 | 增强可替换性或运行韧性 | 仅支持多 API 不等于智能路由 |
| 可观测与追踪 | 输入输出、版本、工具轨迹、token/延迟、反馈 | 支持回放、定位和评估 | 隐私与敏感数据处理 |
| 推理/性能 | 并发、流式、批处理、缓存、量化、资源 | 有口径的延迟/吞吐/成本变化 | 硬件、模型、负载和质量变化 |
| 工程交付 | API、权限、测试、CI、部署、监控 | 稳定集成到真实系统 | 不能只写模型调用代码 |

## 3. 成果表达

虚构脱敏示例：

> 为知识问答流程设计带来源引用的检索与回答约束，并建立覆盖缺失文档、冲突信息和越权请求的回归样例，使模型版本调整能够被重复评估和追踪。

这不等于“幻觉率下降”，除非有明确定义、样本、基线和确认数据。

Agent 项目应说明工具、状态、失败恢复和授权边界，避免只写“使用 Function Calling 构建智能 Agent”。

## 4. AI/LLM 禁忌

- 把调用 OpenAI 兼容 API 写成模型研发或算法主导。
- 罗列 RAG、Agent、MCP、Function Calling、Prompt 等热词，没有真实机制与结果。
- 没有评估集/口径就写准确率、召回率、幻觉率、延迟或成本改善。
- 声称“彻底消除幻觉”“完全自主”“保证不泄露”或“多智能体提升效率”。
- 将模型生成的内容质量主观感受当成业务结果。
- 把个人 demo 包装成公司上线产品，或隐藏公司后端背景。
- 在简历中复制 Prompt、私有文档、内部工具 schema、模型密钥或用户对话。
- 为 JD 虚构微调、训练、向量检索规模或生产流量。

## 5. 高价值追问

1. 为什么这个问题需要大模型，确定性规则/搜索为何不够？
2. 你亲自负责 Prompt、检索、工具、评估、后端还是部署的哪些边界？
3. RAG 的切分、检索、重排和引用如何设计，如何处理无答案/冲突资料？
4. Agent 工具有哪些副作用，权限、幂等、超时和失败恢复如何处理？
5. 评估集从哪里来，覆盖哪些失败类型，人工与自动评估如何校准？
6. 模型选择比较了质量、延迟、成本、上下文和安全的哪些取舍？
7. 如何防止提示注入、越权访问、敏感输出和不可追踪调用？
8. 指标是在什么模型版本、数据集、环境和统计窗口下获得？
9. 哪些场景仍然失败，如何兜底和监控？

## 6. 职业阶段差异

- **应届/实习**：突出可运行项目、评估严谨性、软件工程基础和失败边界；教程式聊天界面不足以支撑“AI 工程专家”。
- **有经验工程师**：公司 AI 项目若真实存在则优先；否则以原公司工程成果为主体，个人/开源 AI 项目作明确补充。
- **技术转型者**：展示原方向可迁移能力（API、数据、可靠性、部署）与真实 AI 转型证据，说明当前深度，不虚构年限。
- **高级工程师**：评估体系、架构取舍、模型/供应商治理、可靠性、安全、成本和跨团队落地更重要。
- **技术负责人/架构师**：叠加负责人策略，验证 AI 系统边界、风险决策与技术参与，不能把团队实验全归个人。

## 7. JD 定制提示

- “RAG”：只接入向量库为部分证实；检索策略、评估、权限、引用和失败处理构成更强证据。
- “Agent”：需要工具契约、状态/编排、失败恢复、权限与观测；一次 Function Calling 不足。
- “Prompt 工程”：需要版本、评估和系统约束；写几段提示词不是高级能力。
- “微调/训练”：必须有数据、训练和评估事实；API 使用不能映射。
- “模型平台/网关”：需要路由、协议、配额、审计、观测或运营证据；封装 SDK 是部分证实。
- “LLMOps”：评估、版本、追踪、部署/监控至少有实际闭环。
- 指定模型/供应商只能在真实使用时写；OpenAI 兼容协议经验不等于使用过所有模型。

## 8. 可辩护性检查

用户应能解释非模型替代方案、RAG/工具的数据与权限路径、评估集、模型选择、失败模式、隐私和成本口径。任何“提升准确率/降低幻觉/自主完成”都必须有定义和验证；否则降级为真实机制或定性结果。
