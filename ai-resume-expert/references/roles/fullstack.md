# 全栈工程师岗位策略

全栈不是把一份前端简历和一份后端简历拼接，而是证明用户能围绕一个产品/系统边界完成端到端设计、交付与运行，并清楚说明深度主次。

## 1. 路由门槛

先确认三个条件：

1. 目标 JD 本身是否需要真实全栈能力。
2. 用户是否在同一项目中承担过前端、后端和交付链路的实质工作。
3. 用户的主专长是什么，另一侧达到什么可辩护深度。

若只是在一个前端项目和一个后端项目分别做过少量任务，通常制作单方向版本更清晰。真正交叉时，以目标 JD 的核心问题决定前后端篇幅，不追求 50/50。

## 2. 优先寻找的证据

- 端到端用户/业务流：从界面交互、API 契约、领域/数据模型到部署与观测。
- 跨边界取舍：数据在哪一层验证、缓存、分页、权限、错误处理和一致性。
- 交付闭环：测试、环境配置、迁移、发布、监控和线上反馈。
- 主技术域深度：至少一侧有复杂问题处理，另一侧能独立交付，不是两边只懂皮毛。
- 接口协作：契约版本、兼容、错误模型、类型共享或文档化。
- 真实结果：减少跨层返工、提升交付可控性、改善具体用户路径；数字需有依据。

## 3. 推荐信息架构

- 个人简介明确“全栈主线 + 主专长”，例如“以后端为主、能独立完成 Web 产品闭环”。
- 核心技能按“前端 / 后端与数据 / 工程交付”分类，每类只留有证据能力。
- 公司项目围绕端到端问题写 2～4 条，不把同一项目拆成重复的前端和后端项目。
- 若目标实际偏一侧，优先展示该侧强证据，另一侧作为协作/闭环补充。

虚构脱敏示例：

> 围绕审批配置流程，设计前端状态模型与后端校验接口，统一错误反馈和权限边界，并补充端到端回归用例，使复杂配置的提交与问题定位更可控。

只有用户确实设计了两侧边界才能使用该表达。

## 4. 全栈禁忌

- 把“会 React + Spring Boot”直接等同于全栈。
- 技能表各列十几个前后端工具，但经历没有端到端证据。
- 前后端各复制一次同一功能，浪费篇幅。
- 两侧都用“精通”，却无法解释运行机制或复杂故障。
- 把个人小型 CRUD 项目写成企业级全栈架构。
- 忽略测试、部署、观测和安全，只写页面 + API。

## 5. 高价值追问

1. 哪个项目最能证明你从用户交互负责到了服务/数据边界？
2. 该项目中前端、后端、数据和部署分别哪些由你亲自完成？
3. 你在哪一侧最深，另一侧能独立处理到什么复杂度？
4. 一项跨层决策（权限、校验、分页、缓存、错误）为什么放在该层？
5. 接口变更如何保持两端兼容并测试？
6. 线上问题如何跨浏览器、服务和数据库追踪？
7. 端到端结果如何观察，是否有可靠口径？

## 6. 职业阶段差异

- **应届/实习**：用一个完整但真实规模的项目证明需求到部署闭环，避免称“架构平台”。强调基础、测试和错误处理。
- **有经验工程师**：公司端到端项目为主，说明长期运行、协作边界和复杂问题；个人项目只作补充。
- **转型者**：明确原主域和新增能力，转型项目证明跨层闭环，不隐藏深度不均衡。
- **高级工程师**：突出边界设计、系统演进、质量/安全、端到端观测和交付取舍。
- **技术负责人**：叠加负责人策略，验证跨端决策权与团队影响，不能将“协调两端”包装成亲自实现全部。

## 7. JD 定制提示

- 将 JD 要求分成前端深度、后端深度、数据、云/交付和产品闭环，判断主次。
- JD 偏后端的全栈岗位：加载 `backend.md` 为主，前端只呈现真实独立交付和接口协作。
- JD 偏前端的全栈岗位：加载 `frontend.md` 为主，后端呈现 API/数据/部署能力。
- “独立负责全栈”需真实端到端边界；只参与联调标为部分证实。
- 不因 JD 同时列出两套技术栈，就把用户未证实技能加入简历。

## 8. 可辩护性检查

用户应能画出请求/数据/发布路径，说明两侧个人边界、关键契约、失败处理、测试、部署和结果。若只能深入解释一侧，简历应如实体现主次，必要时改为单方向版本。
