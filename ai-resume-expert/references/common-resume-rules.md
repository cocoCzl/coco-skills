# 程序员简历通用规则

本文件适用于所有首版技术岗位。岗位策略只能改变证据优先级，不能放宽真实性、归属、保密和可辩护性规则。

## 1. 成功标准

优秀程序员简历应让招聘者在短时间内回答三个问题：

1. 候选人能解决哪类目标岗位问题？
2. 候选人处理过何种复杂度和约束的系统？
3. 哪些行动与结果可以明确归属于候选人？

“投递就绪”只表示事实、目标、保密、结构和版式已过门槛，不代表 ATS 保过、获得面试或录用。

## 2. 不可突破的真实性边界

- 不编造职位、年限、项目、职责、技术、数字、客户、影响或主导权。
- 项目存在某能力，不等于用户实现过该能力；团队获得某结果，不等于用户独立达成。
- 原简历中的文字仍是待核实材料，不因“已经写过”自动成为事实。
- 用户明确确认的真实经历可以进入职业事实真源，即使没有外部材料佐证。
- 互斥事实在澄清前阻断相应陈述，不能选择“更好看”的版本。
- 无可靠数字时使用真实定性结果；不得从代码行数、组件数量或模型感觉推算业务收益。
- 每个高强度动词和高熟练度技能都必须经得起“你具体做了什么”的追问。

## 3. 默认信息架构

章节按证据价值动态出现，不要求每人填写固定模板。

### 核心章节

1. 最小必要个人信息：姓名、手机、邮箱、城市、专业主页和单一目标岗位。
2. 个人简介：3～5 行，概括职业阶段、核心方向、代表性问题与目标岗位，不写空泛性格评价。
3. 核心技能：按能力域分类，且能在经历中找到支撑。
4. 主要证据章节：工作经历、实习经历或教育/项目，依据职业阶段排序。
5. 教育经历：学校、专业、学历、时间；有工作经验后从简。

### 条件章节

精选项目、开源贡献、论文/专利、竞赛、证书和奖项只有在与目标岗位相关且有证据时出现。通常删除无证据自我评价、无关兴趣、低价值课程和与目标无关的工具清单。

### 职业阶段差异

| 职业阶段 | 章节优先级 | 主要证据 | 常见风险 |
|---|---|---|---|
| 应届/实习 | 教育/实习 → 项目/竞赛/开源 → 技能 | 学习基础、真实实践、个人作用、成长速度 | 把课程作业写成商业系统；只列课程和技术名 |
| 有经验工程师 | 简介/技能 → 工作经历中的公司核心项目 → 教育 | 系统复杂度、个人行动、技术取舍、真实结果 | 工作与项目章节重复；个人项目挤占公司证据 |
| 技术方向转型 | 原方向公司证据 → 可迁移能力 → 明确标注的转型证明项目 | 既有工程能力、真实新方向实践、转型连续性 | 隐去原背景；把练习项目包装成公司业务 |
| 技术负责人/架构师 | 影响摘要 → 决策/演进/跨团队证据 → 技术深度 | 决策边界、替代方案、迁移、影响范围、结果 | 把团队一切成果归为个人；只写管理动作 |

## 4. STAR 证据与正式表达

STAR 用于访谈和核实，不把正文写成四段标签。

- S（场景）：问题、约束、规模、风险或为什么要做。
- T（任务）：用户被要求承担的边界、角色和成功条件。
- A（行动）：用户亲自设计、实现、排查、推动或验证的动作及取舍。
- R（结果）：可核查数字或不夸大的真实定性结果。

适合正文的压缩结构：

> **具体动作 + 技术/方法 + 真实结果（必要时补充场景/约束）**

虚构脱敏示例：

- 弱：负责消息模块开发，使用 Redis 和线程池。
- 强：针对批量通知占用请求线程的问题，设计独立任务队列与失败重试记录，使接口可快速返回，并增强异常任务的可追踪性。

第二句不含未经确认的百分比，也没有把“系统全部稳定性”冒领为个人成果。

### 动词强度与证据

- “参与”：能说明自己的具体部分，不能以此掩盖归属不清。
- “实现/排查/重构”：需要能解释实现边界、判断过程和结果。
- “设计/主导/推动”：需要决策权、替代方案或协作影响的确认。
- “负责整体/架构”：需要范围、持续时间、关键决策与实际承担证据。

优先使用设计、实现、重构、优化、排查、定位、搭建、接入、封装、迁移、自动化、标准化等具体动作；不要机械地把每条都写成“负责”。

## 5. 量化规则

### 可以使用

- 有来源且用户确认的前后对比：例如来自监控或测试记录的 P95 延迟变化。
- 可说明口径的规模：服务数、模块数、数据量、请求量、支持平台数等。
- 可复算的结果：原来与现在的耗时、人工步骤数、错误数或资源成本。
- 用户只记得范围时，可在其确认后写“数十个”“多个业务线”等范围表达。

### 不可以使用

- “效率提升 300%”“性能提升 90%”但没有基线、口径或来源。
- 从代码复杂度推导用户量、收入、节省成本或稳定性。
- 把团队或产品整体指标写成个人直接贡献，除非能说明影响链条和个人边界。
- 用“业内领先”“大幅提升”“显著优化”等形容词代替结果证据。

### 量化确认最小记录

记录指标名称、基线、结果、统计窗口/样本、来源、用户能否披露，以及用户确认时间。信息不全时降级为真实定性结果，例如“减少重复手工配置”“使失败任务可追踪”“统一发布流程”。

## 6. 技能熟练度

技能按编程语言、框架与平台、数据与中间件、工程与交付、岗位专属能力等能力域分类。

- “熟练”：项目中经常使用，能够独立完成并处理较复杂问题。
- “熟悉”：能够独立完成常见任务，并解释主要机制和边界。
- “了解”：有学习或有限实践，但不应抢占核心技能位置。
- “精通”：只有在持续复杂实践、底层理解和面试可辩护性均很强时使用，且需用户确认。

禁止技能百分比、星级、进度条、无经历支撑的关键词和“全部精通”。技能列表必须与经历互相印证；无法找到支撑的技能应降级、删除或列入证据差距。

## 7. 公司项目、个人项目与重复控制

- 有经验用户以公司核心项目为主体，项目作为对应公司经历的一部分呈现。
- 工作概述写职责范围与持续影响；项目要点写代表性问题、个人行动和结果。两处不得复制同一句。
- 默认选 2～4 个最有价值项目，而不是写完全部项目。
- 普通个人项目只作补充，不挤占更强的公司证据。
- 转型证明项目可成为关键补充，但必须明确标注“个人项目”或“开源贡献”，不能伪装成公司经历。
- 项目简介只需一句说明解决什么问题；正文不是产品功能列表。

## 8. ATS 与 JD 边界

- 使用标准章节标题、普通文本、稳定层级、单栏阅读顺序和可识别日期。
- 允许把真实经历改写为 JD 使用的等价术语，例如将已证实的“接口幂等控制”映射为“可靠 API 设计”。
- 任何进入正文的 JD 关键词必须关联职业事实；未证实要求只进入证据差距。
- 禁止隐藏白字、关键词堆砌、伪造工具经历、ATS 分数和录用概率。
- 没有具体 JD 时只能称岗位基准版，不能声称已经与某个职位匹配。

ATS 友好不等于牺牲人类阅读体验。清晰的动词、简短段落、统一日期、常见标题和可选择文本同时服务招聘者与解析系统。

## 9. 最小信息与保密

默认保留姓名、手机号、邮箱、所在城市、专业主页、目标岗位。默认不加入照片、性别、生日/年龄、婚姻、籍贯、身份证号、民族、身高体重和期望薪资。

涉及公司材料时使用最小披露原则：

- 内部项目代号改为安全业务类别，如“企业级权限治理平台”。
- 客户、域名、IP、账号、表名、内部接口、安全配置和源码不进入简历。
- 保留问题类型、用户个人动作、通用技术方法和可披露结果。
- 仅替换项目名不等于完成脱敏；仍需检查上下文是否可反推出客户或架构。

## 10. 篇幅与可读性

- 工作经验较少通常 1 页；证据充足的 3 年以上候选人可以 2 页。
- 不为强行压页使用难以阅读的小字号、极窄边距或密集长段落。
- 每段任职通常保留 3～6 个高价值要点；相似低价值要点合并。
- 每个要点优先表达一个主要成果，避免把多个无关动作串成超长句。
- 日期、公司、岗位和项目归属要一眼可读。

## 11. 发布前通用红线清单

出现任一项时不得标记投递就绪：

- 未解决的事实冲突、保密阻断或待确认个人贡献。
- 目标岗位/目标职级缺失，或多个不相干岗位混在一个标题中。
- 核心成果缺少个人角色、行动或真实结果。
- 技能与经历无法互证，或含无证据“精通”。
- 无依据数字、团队成果冒领、内部敏感标识或源码细节。
- 大量占位符、明显时间线矛盾、工作/项目重复。
- 用户无法解释核心成果或高熟练度技能。
