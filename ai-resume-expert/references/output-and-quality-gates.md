# 输出模板、自审、可辩护性与 PDF 交付门槛

用户可见 Markdown 初稿必须是经过事实、岗位、保密、重复、篇幅和可辩护性检查的版本，不能直接交付模型第一次生成文本。

## 1. 阶段与可交付物

| 阶段 | 可交付 | 不得声称 |
|---|---|---|
| 信息不足 | 素材清单、信息缺口、项目建议、简历骨架 | Markdown 初稿、投递就绪 |
| 证据达标 | 自审后的 Markdown 初稿、证据追踪、JD 覆盖、修改对照、面试追问的适用子集 | 已定稿、PDF 已确认 |
| 用户确认 Markdown | 最终 Markdown、可打印 HTML；联系方式确认后可进入 PDF | 未验收 PDF 为投递就绪 PDF |
| PDF 验收通过 | PDF、最终 Markdown、必要的验收摘要 | ATS 保过、面试/录用保证 |
| PDF 失败 | 最终 Markdown、可打印 HTML、失败原因 | PDF 已生成或视觉已验收 |

## 2. 简历素材清单模板

```markdown
# 简历素材清单

## 定位
- 目标岗位 / 职级 / 职业阶段：
- 版本：岗位基准版 / JD 定制版

## 已确认职业事实
按任职、项目、技能、教育列出，注明可披露状态。

## 待确认素材
只列候选，不写成事实。

## 信息缺口
按“阻断初稿 / 影响质量 / 可后补”排序。

## 证据冲突与保密阻断
逐项说明受影响陈述；无则明确写“未发现”。
```

## 3. 项目建议模板

```markdown
# 项目入选建议

| 顺序 | 项目与归属 | 建议 | 对目标岗位的证据 | 取舍理由 | 待确认/风险 | 建议位置 |
|---:|---|---|---|---|---|---|

最终选择权归用户；公司核心项目默认放在对应公司经历下。
```

## 4. Markdown 简历结构

结构随职业阶段变化，下列是组件而非所有人必填模板。

### 最小页首

```markdown
# 姓名
目标岗位（单一定位）

城市｜手机号｜邮箱｜GitHub/博客/技术主页（仅保留真实且有价值的链接）
```

Markdown 初稿阶段联系方式可暂缺，使用“待定稿前补充”的会话提示，不要在正文放大量 `TODO`。最终 PDF 前必须补齐并由用户确认。

### 有经验工程师

```markdown
## 个人简介
3～5 行：年限/阶段、核心方向、代表性系统问题、可证明优势、目标岗位。

## 核心技能
按能力域分类；每项能在经历中找到支撑。

## 工作经历
### 可披露公司名｜岗位｜YYYY.MM—YYYY.MM/至今
一句职责范围与技术主线（可选）

**项目名｜技术栈：** 5～10 项与本项目实际实现相关的精选技术

- 项目背景/约束 + 个人行动 + 技术/方法与必要取舍 + 真实结果
- 另一项不重复的高价值证据

## 个人/开源项目（仅在相关且有价值时）
## 教育经历
```

### 应届/实习

```markdown
## 教育经历
## 实习经历
## 精选项目 / 竞赛 / 开源（按证据价值选择）
## 核心技能
```

### 技术方向转型

以真实公司经历为主体，明确展示可迁移能力；另设“个人项目”或“开源贡献”作为转型证明，不伪装归属。

### 技术负责人/架构师

个人简介先概括技术主域与影响边界；工作经历优先呈现关键决策、方案取舍、系统演进、跨团队影响和结果，同时保留亲自参与的技术深度。

## 5. 成果要点质量模板

每条先在证据层完成 STAR，再压缩为：

> [场景/约束，可选] + [个人具体动作] + [技术/方法与必要取舍] + [可核查量化或真实定性结果]

检查：

- 能圈出用户亲自做的动作，而非只描述系统功能。
- 动词强度与个人决策权相符。
- 技术名为说明问题服务，而非关键词堆砌。
- 结果真实，因果边界合理；无可靠数字不写数字。
- 句子可在一次呼吸内理解，必要时拆分。
- 正文不显示 S/T/A/R 标签。

## 6. JD 覆盖输出模板

```markdown
# JD 要求覆盖

| 要求 | 已证实/部分证实/未证实/不相关 | 支撑事实 | 正文处理 | 证据差距 |
|---|---|---|---|---|

未证实要求只留在证据差距，不进入简历正文。不输出 ATS 百分比。
```

## 7. 生成后自审

### 事实与归属

- [ ] 每条核心陈述能在证据追踪表找到来源、用户确认和可披露状态。
- [ ] 项目事实没有被自动写成个人贡献；团队结果的个人边界清晰。
- [ ] 无未解决冲突、待确认贡献、无依据数字或扩大的因果。

### 岗位与内容

- [ ] 单一目标岗位与职级明确；无 JD 时标明岗位基准版。
- [ ] 内容应用了目标岗位策略和职业阶段结构。
- [ ] 核心技能均有经历支撑；无百分比、进度条或无证据“精通”。
- [ ] 项目通常 2～4 个；多段相关任职均有清晰、可辩护且与目标相关的项目证据时可采用 4～5 项（最近 2～3 项、其他相关任职各 1 项），公司核心项目归入对应任职。
- [ ] 每段保留任职已判断是否保留代表项目；只有经历摘要的任职有明确的重复、证据、保密或篇幅理由。
- [ ] 工作概述和项目成果不重复，没有功能清单和空泛自评。
- [ ] 每个入选项目都有 5～10 项可追溯的精选技术栈；页首核心技能均有已确认的个人经历支撑，而不是依赖清单或项目技术的无差别汇总。

### JD 与 ATS

- [ ] 每个进入正文的 JD 关键词都有职业事实支撑。
- [ ] 未证实要求只在证据差距；无隐藏词、堆词、假分数。
- [ ] 标题、日期、层级和链接使用稳定、可解析的文本结构。

### 保密与可读性

- [ ] 无客户、内部项目代号、域名/IP、表/接口、安全配置、源码或敏感数字。
- [ ] 默认 1～2 页，未通过缩小字号强行压页。
- [ ] 最小必要个人信息；无默认照片和无关敏感身份字段。

### 可辩护性

- [ ] 每条核心成果可解释背景、个人作用、取舍和结果依据。
- [ ] 高熟练度技能可说明复杂实践、原理与边界。
- [ ] 不能解释的陈述已降级、补充或删除。

任一阻断项失败，回到访谈/证据治理，不得将初稿标记为投递就绪。

## 8. 面试可辩护性清单

面试问题独立交付，不进入简历正文。每条核心成果至少选择适用问题：

1. 当时的具体场景、约束和成功条件是什么？
2. 团队如何分工，你个人从哪里负责到了哪里？
3. 为什么选择该方案？比较过哪些替代方案？
4. 最难的问题如何定位？哪一步判断最关键？
5. 结果如何测量或观察？指标口径和数据来源是什么？
6. 方案有什么代价、失败情况或后续改进？
7. 如果重新做一次，会改变什么？

高熟练度技能还应问：

- 你独立处理过的最复杂场景是什么？
- 关键机制、常见误区和边界条件是什么？
- 何时不应使用它，替代方案是什么？
- 简历中哪段经历最直接支撑该熟练度？

### 处理无法辩护的陈述

- 用户只做了局部实现：把“主导/设计整体”降为真实动作。
- 结果口径不清：删数字，保留真实定性结果。
- 只知道术语：从核心技能移除或降为“了解”。
- 涉及不可披露信息：泛化到安全业务类别或删除。

## 9. 投递就绪门槛

必须同时满足：

- 最低证据门槛和生成后自审通过。
- 诊断中的致命问题已解决；无事实冲突和保密阻断。
- 用户已经审阅并明确确认最终 Markdown 的事实、措辞和项目选择。
- 联系方式已补齐并确认。
- 面试可辩护性通过；无大量占位符。
- 预计可控制在 1～2 页，并符合单栏 ATS 结构。

状态说明应为“内容已满足本 Skill 的投递就绪门槛”，同时明确不保证 ATS、面试或录用结果。

## 10. PDF 前置门槛

只有以下条件全部满足才启动 PDF：

1. 用户明确说已确认当前 Markdown，而非沉默或只说“看起来还行”。
2. 姓名、手机、邮箱、城市及要展示的链接已由用户确认。
3. 事实、保密与可辩护性无阻断。
4. 默认输出目录为当前工作区的 `reports/ai-resume-expert/`；用户明确指定其他位置时仍须在 Skill 包外。
5. 使用本地渲染能力，不上传私人材料到第三方转换服务。

## 11. 默认 PDF 视觉规范

- 现代技术型极简风，单栏主体，克制深蓝/深灰强调色。
- 清晰的姓名、目标岗位、章节标题、公司/项目和正文层级。
- 统一网格、日期对齐、细分隔线和充足但不浪费的留白。
- 中文字体有合法的本地回退策略；正文字号保持易读。
- 文字可选择，阅读顺序稳定，链接可点击，黑白/灰度仍清晰。
- 页首外链使用短标签 Markdown 链接，不堆叠完整裸 URL。
- 禁止双栏主体、技能进度条、复杂图表、花哨背景、隐藏关键词和图片型正文。
- 默认 1～2 页；先删弱证据、合并重复和精炼文案，不先缩小字号。

## 12. PDF 验收

文件存在不等于通过。至少检查：

- [ ] 页数为 1～2 页，页面尺寸与边距稳定。
- [ ] 可提取完整中文文本，顺序与视觉一致，无乱码或缺字。
- [ ] 页面渲染图已实际检查字体、层级、对齐、留白和整体专业感。
- [ ] 无截断、重叠、异常换行、标题孤立或明显孤行寡行。
- [ ] 链接显示与目标正确，长链接未破坏布局。
- [ ] 灰度/黑白检查仍有足够对比，不依赖颜色理解结构。
- [ ] 未通过不可读小字号、极窄行距或边距强行压页。

发现问题时阻断 PDF 交付，调整内容/版式后重新渲染和验收。

## 13. PDF 失败降级

渲染依赖不可用、字体失败、文件超页或多次修正仍不合格时，交付：

1. 已确认的最终 Markdown。
2. 单栏、可打印、使用系统字体回退的 HTML。
3. 清楚说明“PDF 未生成/未通过验收”的原因和未检查项。
4. 可执行的后续建议，例如安装本地渲染器或改用用户已有的受信工具；不得上传到第三方在线转换服务。

不得把失败生成物标成最终 PDF。

## 14. 最终交付摘要模板

```markdown
## 交付状态
- 版本：岗位基准版 / JD 定制版
- 内容：Markdown 已确认 / 未确认
- 投递就绪门槛：通过 / 未通过（原因）
- PDF：已生成并验收 / 未生成，已降级为 Markdown + 可打印 HTML
- 页数与视觉：<仅在实际验收后填写>
- 重要边界：不保证 ATS 通过、面试或录用
```
