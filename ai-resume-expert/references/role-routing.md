# 目标岗位路由、交叉定位与有限降级

目标岗位是第一道门槛。用户未说明目标岗位时，只自然询问目标岗位，不生成简历初稿，也不抢先发送批量问卷。

## 1. 先区分三个概念

- **目标岗位**：这份简历准备申请什么。
- **当前职业背景**：用户真实做过什么，是证据来源。
- **目标职级**：希望申请初级、中级、高级、技术负责人或架构师等层级。

当前是 Java 后端但想申请 AI 应用工程师时，目标岗位是 AI/LLM 应用；Java 经历是可迁移的当前背景，不能因为目标改变而重写成“长期 AI 算法经验”。

## 2. 首版岗位规范化

| 用户常见表述 | 规范岗位族 | 策略文件 | 需继续确认 |

| Web 前端、前端工程师、可视化前端 | 前端 | `roles/frontend.md` | Web/可视化/工程化重点、职级 |

| Android、iOS、Flutter、React Native、桌面客户端 | 客户端/移动端 | `roles/client-mobile.md` | 平台、原生/跨端、端侧重点 |
| 测试开发、SDET、自动化测试、质量平台 | 测试开发 | `roles/test-development.md` | 自动化/平台/性能/质量方向 |

## 3. 模糊目标的单问示例

- “想做开发”：`你更希望这份简历申请哪一类开发岗位？例如后端、前端、全栈或移动端。请先选最主要的一个方向。`
- “AI”：`你目标更接近模型/算法研发，还是基于模型做 RAG、Agent 和业务应用的 AI 工程？这会决定证据重点。`
- “运维”：`目标更偏日常运维、DevOps 交付自动化、SRE 可靠性，还是内部平台工程？`
- “架构”：`你要申请的是仍以技术决策和系统演进为核心的架构师，还是纯管理岗位？首版只深度支持前者。`

一次只问一个决定路由的问题。

## 4. 多目标岗位

明显不同的目标通常分别制作版本，例如：

- 后端工程师 + 测试开发
- 数据工程师 + 算法工程师
- 前端工程师 + DevOps

说明不同岗位关注的证据不同，并请用户先选择当前版本。不要生成“Java 后端 / 测试开发 / AI / 运维”并列通投标题。

## 5. 真正的交叉岗位

岗位本身要求两类能力且用户有两边证据时，可以合并：

- 后端 + AI/LLM 应用：AI 应用后端、Agent 平台工程。
- 全栈：真实负责前后端闭环，而非分别做过两个孤立小任务。
- SRE + 平台工程：围绕可靠性和内部平台自服务的一体岗位。
- 数据工程 + ML 工程：数据/特征管道与模型生产化都在 JD 和事实中占核心。

确认三个条件：JD 是否真实交叉、用户两侧证据是否足够、能否用一个清晰岗位标题解释主线。若任一不满足，拆分版本。

组合策略时指定主次：主策略决定简介、项目排序和篇幅；次策略只补充 JD 必需且已证实的能力，不能拼接两份完整简历。

## 6. 职业阶段与目标职级

岗位路由后再确定职业阶段：应届/实习、有经验工程师、技术方向转型、技术负责人/架构师。目标职级不能仅按年限推断：

- 初/中级侧重独立交付、基础质量和问题解决。
- 高级侧重复杂约束、方案取舍、稳定性和跨模块影响。
- 技术负责人/架构师侧重决策权、系统演进和跨团队影响，同时验证技术深度。

用户可申请高于当前头衔的职级，但简历只能呈现真实证据；证据不足应提示差距，不补造职责。

## 7. 市场、语言与 JD

- 首版默认目标求职市场为中国大陆、简历语言为中文。
- 简历语言与求职市场不同：翻译成英文不等于具备海外市场专家适配。
- 有 JD：生成 JD 四态覆盖和定制版。
- 无 JD：生成岗位基准版，不声称具体 ATS/JD 匹配。

## 8. 有限降级

以下目标不在首版专家范围：产品/项目管理、UI/UX、纯技术支持、硬件电子、纯管理，以及其他非技术职业；海外市场、学术 CV 也不提供专家级适配。

降级时：

1. 明确首版深度支持范围和当前限制。
2. 可提供通用事实整理、STAR 梳理、基础结构/真实性诊断。
3. 不套用最相近程序员模板冒充岗位策略。
4. 不标记专家优化或投递就绪。
5. 如用户同时有受支持技术目标，请其选择是否切换。

建议话术：

> 这个目标岗位不在首版深度支持范围内。我可以继续帮你做通用事实整理和基础简历诊断，但不会声称完成该职业的专家级优化或把结果标记为投递就绪。如果你准备申请的是受支持的技术岗位，请告诉我具体方向，我会切换到相应策略。
